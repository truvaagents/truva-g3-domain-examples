Slow down: what is one search candidate?

A candidate is a ranked search result. It includes the normalized section and source so the agent can inspect the possible match. Think of it as a library copy marked “possible match”: it helps the agent choose, but it is not the signed policy proof that Commerce Core accepts. 

{
  "section": {
    "section_id": "demo-auto-recovery-bounds",
    "title": "Bounded automatic recovery options",
    "content": "After eligibility is supported ..."
  },
  "source": {
    "source_id": "commerce-demo-recovery-standard",
    "title": "Commerce Demo Recovery Standard v1"
  },
  "score": 0.032522,
  "retrieval": "rrf(bm25+semantic)"
}
  1. The nested section ID is the address used for the later exact read. Search also provides preview data.
  2. The score only places this result ahead of other candidates.
  3. The nested source helps the agent judge provenance, but the selected section is still exact-read next.
  4. No signed receipt is present yet. Therefore this object cannot authorize a command.

What happens when the gateway pod starts?
  1. Open: read the selected domain pack from disk.
  2. Strict decode: reject malformed JSON and unknown fields instead of silently guessing.
  3. Validate: reject duplicate IDs, broken source references, bad relation endpoints, and invalid release data.
  4. Hash: calculate the canonical SHA-256 identity used throughout the run.
  5. Build retrieval view: prepare tokens, aliases, scope metadata, and dates for deterministic filtering and ranking.
  6. Project graph: load section nodes and typed links into embedded LadybugDB.
  7. Serve: expose the same four public capabilities to any compliant agent.

X-ray 7

The exact search algorithm

There is no LLM, embedding API, or vector database inside this search path.

  1. 1
    Validate

    Require query, tenant, jurisdiction, channel, and RFC3339 decision time.

  2. 2
    Hard-filter

    Remove the wrong release, tenant, jurisdiction, channel, effective date, and optional tags.

  3. 3
    Lexical rank

    BM25-style scoring over title, content, and tags, with a reviewed priority boost.

  4. 4
    Alias-vector rank

    Reviewed aliases plus terms and bigrams hashed into 128 buckets; cosine similarity.

  5. 5
    Fuse

    Reciprocal-rank fusion with k=60; named-source preference when applicable.

  6. 6
    Attach graph clues

    At most twenty authored one-hop paths from the ranked sections.

Lane A

BM25-style lexical ranking

Good for exact domain terms such as “same-SKU,” “inventory,” “restricted,” and “approval.”

rank＋rank↓RRF

Lane B

Deterministic alias-aware similarity

Connects reviewed vocabulary such as “reship” and “replacement,” but cannot discover unseen domain meaning.

Read the score correctly: 0.032522 is a reciprocal-rank fusion value. It is not 3.25% confidence, not a correctness probability, and not permission to act.
Worked example: follow one query through all six stages
  1. Input arrives: “same-SKU replacement ...” plus commerce-demo / US / online / 2026-08-20T18:00:00Z.
  2. Hard scope runs first: sections for another tenant, another jurisdiction, a store-only channel, or the wrong effective date are removed before scores matter.
  3. Lexical lane notices: exact words such as replacement, inventory, fraud, restricted, and approval.
  4. Alias lane expands reviewed vocabulary: for example, reship is treated like replacement and lost like missing.
  5. RRF combines positions: a section ranked well in both lists moves near the top. It does not convert rank into probability.
  6. Graph clues are attached: the top section points to approval, precedence, and follow-up sections that humans already linked in the pack.

Result: demo-auto-recovery-bounds ranked first. The agent then used its relation clues to exact-read the approval and precedence sections too.

X-ray 8

LadybugDB without the mystery

Embedded in the gateway pod

A disposable graph projection, not the canonical corpus

The JSON pack remains authoritative and can rebuild the graph whenever the pod starts.

In-memory reference store
  • Applies hard scope and date filters.
  • Runs lexical and alias-vector ranking.
  • Calculates allowed traversal paths.
  • Returns the exact section and source.
LadybugDB projection
  • Stores section nodes and typed links.
  • Confirms an exact-read node exists.
  • Confirms allowed edge triples exist.
  • Uses 128 MB buffer and two threads in this demo.

Both are behind the provider-neutral KnowledgeStore interface. Replacing LadybugDB with Neo4j should change the adapter, not the public gateway API or the agent plan.

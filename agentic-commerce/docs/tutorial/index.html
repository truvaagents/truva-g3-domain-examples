Business question

Can the company create a replacement automatically?

A correct answer depends on current order facts, company authority, carrier or seller rules, evidence validity, approval thresholds, and the risk of processing the same request twice.

What a human operations specialist normally does

  1. 1
    Open the order.

    Check payment, fulfillment, carrier, inventory, value, risk, restrictions, and the current order version.

  2. 2
    List possible actions.

    For example: wait, refund, replace, cancel, or file a carrier claim.

  3. 3
    Find the policies that apply.

    Search public rules, carrier terms, seller policies, and internal company policy.

  4. 4
    Resolve exceptions and conflicts.

    Check dates, market, product category, carrier, and whether a narrow rule overrides a general rule.

  5. 5
    Make an authority decision.

    Decide whether the action is allowed, denied, missing evidence, conflicting, or needs approval.

  6. 6
    Perform the action safely.

    Confirm that the order and policy have not changed. Prevent a duplicate refund or replacement.

  7. 7
    Verify and communicate.

    Check the final order state and then notify the customer.

Investigation complete
→
AllowedAct automatically
Approval requiredPause for a person
DeniedDo not act
Not enough certaintyStop and explain why
The automation goal

Use AI to coordinate the investigation. Keep policy authority, approval, order changes, duplicate protection, and verification in normal software that can enforce exact rules.

Chapter 3

Where AI helps—and where it does not

The language model is useful when the path is not known in advance. It is not trusted to authorize or change an order.

Uses a language model

The agent investigates

  • Understands the order-risk request.
  • Chooses which read-only capabilities to call.
  • Searches for relevant policy evidence.
  • Follows useful policy relationships.
  • Builds a step-by-step investigation.
  • Summarises the verified result.
Controlled JSON calls Safety boundary Validated results

Does not use a language model

The tools enforce

  • Return current order and inventory facts.
  • Return exact, dated policy sections.
  • Verify signed evidence receipts.
  • Apply fixed eligibility and approval rules.
  • Reject stale policy or order state.
  • Change and verify the order exactly once.

Do not confuse these two kinds of knowledge

Skill: the operating procedure

A small set of instructions for the agent. It says: read order state first, search the correct scope, read decisive sections, ask the evaluator, never execute a denial, and always verify.

Domain pack: the policy corpus

A versioned collection of policy sections, sources, dates, relationships, search vocabulary, and retrieval tests. Large domain knowledge belongs here, not inside the skill.

Commerce Core under the hood

A rules calculator, safety gate, and transaction owner—not a second AI

Commerce Core is ordinary deterministic software written in Go. It accepts strict JSON, reads current business state, checks proof, and follows explicit if/then rules. It cannot understand a customer sentence, search policy prose, or invent a new rule.

1

Rules calculator

Compares verified order facts with option-specific eligibility rules and monetary thresholds.

2

Safety gate

Rejects missing, conflicting, expired, out-of-scope, stale, or unapproved decision evidence.

3

Transaction owner

Is the only demo service allowed to change an order, and protects that change from duplicates.

What happens inside evaluate_recovery_policy

  1. 1
    Receive a strict case

    Order ID, one option ID, release ID and hash, decision time, exact section IDs, and signed receipts.

  2. 2
    Read current truth

    Commerce Core loads the order itself. It does not trust an order snapshot written or remembered by the language model.

  3. 3
    Validate the proof

    The release must be active. Every section must be known, and every receipt must be valid for the same tenant, place, channel, date, and decision time.

  4. 4
    Run fixed business rules

    Go code checks the selected option against order facts and required section IDs. It does not ask an LLM to interpret the section text.

  5. 5
    Classify the decision

    The result is allowed, approval required, denied, insufficient evidence, or conflicting evidence.

  6. 6
    Store a short-lived basis

    A 15-minute decision token binds the option to the order version, policy release, evidence, and time. Evaluation does not change the order.

How the five outcomes are selected

insufficient_evidenceA decisive section, required receipt, or carrier fact explicitly treated as evidence is missing.
conflicting_evidenceTwo equally applicable rules disagree and no reviewed precedence rule resolves them.
deniedThe evidence is available, but current order facts fail the fixed eligibility rule.
approval_requiredThe action is eligible, but a configured value or restriction threshold requires a person.
allowedThe action is eligible, evidence is sufficient, and no approval threshold is crossed.

Deterministic Commerce Core

Answers a closed business question

  • Accepts only a defined JSON structure.
  • Reads authoritative state from its own store.
  • Uses reviewed section IDs and fixed Go rules.
  • Returns the same outcome for the same valid state and inputs.
  • Can authorize and execute only predefined options.

What the policy corpus does—and does not do

The Knowledge Gateway gives the agent exact policy text for investigation and gives Commerce Core signed proof that specific sections were read. Commerce Core recognises the stable section IDs used by its decision table. It does not translate a new paragraph into executable logic by itself. Adding a document to the corpus can improve retrieval, but it does not automatically add a new business rule.

Worked example · ORD-1003

Why the replacement is allowed automatically

  • Order is missing_in_transit.
  • Replacement inventory is available.
  • Fraud risk is low and the item is not restricted.
  • The replacement-authority section has a valid receipt.
  • Order value is $69; automatic replacement limit is $75.
Valid authority+Facts pass+$69 ≤ $75=allowed

If the same eligible replacement were worth $249, the result would be approval_required when threshold evidence is present. Without that threshold evidence, it would be insufficient_evidence.

How this maps to a real company: A production organisation may split these duties across an order-management system, policy service, payment service, inventory service, approval workflow, and audit ledger. This laptop demo combines them in one small service so the control boundary is easy to see. The control pattern is reusable across domains, but this Go decision table and these order mutations are commerce-specific.

Domain Knowledge Gateway under the hood

A controlled policy library, search pipeline, graph navigator, and evidence notary—not a policy brain

The gateway helps the agent find a small, relevant set of policy sections without putting the whole corpus into an LLM prompt. It applies repeatable retrieval rules and proves exact reads. It does not decide whether a refund, replacement, or other business action is allowed.

1

Release keeper

Loads one versioned domain pack and exposes its release ID, validity, source count, section count, and hash.

2

Scoped retriever

Filters out inapplicable sections before combining two deterministic relevance rankings.

3

Graph navigator

Follows authored links such as REQUIRES, OVERRIDES, and CONFLICTS_WITH.

4

Evidence notary

Returns an exact in-scope section and a signed, 30-minute receipt that Commerce Core can verify.

Inside search_evidence

How a question becomes a ranked candidate list

  1. 1
    Validate the request

    Require a query, tenant, jurisdiction, channel, and decision time. Optionally accept a release, controlled tags, and a result limit.

  2. 2
    Apply hard scope first

    Keep only the active release, matching tenant, applicable place and channel, effective date, and optional OR-matched tags.

  3. 3
    Run two rankings

    Rank the same filtered sections once by word relevance and once by deterministic alias-aware similarity.

  4. 4
    Fuse the rankings

    Reciprocal-rank fusion rewards sections that rank well in either list. Named-source queries suppress unrelated peer sources.

  5. 5
    Return a small result

    Return at most the requested limit—eight by default—plus up to twenty one-hop relation paths from ranked sections.

Ranking lane A

BM25-style word relevance
  • Lowercases and tokenizes title, text, and tags.
  • Removes common words and applies a small stemmer.
  • Rewards useful rare terms and repeated matches.
  • Boosts a section using its reviewed priority.
ranked list＋ranked list↓RRF

Ranking lane B

Deterministic alias-aware similarity
  • Normalizes reviewed aliases from the active pack.
  • Hashes words and neighbouring word pairs into 128 numeric buckets.
  • Uses cosine similarity between query and section vectors.
  • Uses no embedding API, learned model, or vector database.
What “semantic” means in this demo: It can connect reviewed vocabulary such as “reship” and “replacement.” It cannot discover every unseen synonym or understand policy like a person. A missing alias can produce a missed result.

Search output

Candidate—not yet evidence

A search candidate includes the normalized section content, stable ID, source metadata, score, retrieval method, and matched terms. In this demo the content is already visible, but there is no signed receipt. A high score means “inspect this,” not “this action is authorized.”

exact read→proof

Exact-read output

Verified evidence package

read_exact_section checks the release, tenant, jurisdiction, channel, and effective date again. It returns the exact section and source plus a signed receipt scoped to that read.

Evidence receipt

What the 30-minute proof contains

  • Section ID
  • Release ID and release hash
  • Tenant, jurisdiction, and channel
  • Decision time
  • Issue time and expiry time
  • Version and HMAC signature
Readable encoded claims.Tamper-evident HMAC

The receipt is signed, not encrypted. Its purpose is proof, not secrecy. If a caller changes a section, scope, release, or time, the signature no longer matches. The receipt proves an exact read; it does not say that a business action is allowed.

LadybugDB's exact role

A disposable graph projection inside the same gateway pod

pack.json remains the canonical source. The projection can be rebuilt whenever the service starts.

LadybugDB does
  • Store one node for each normalized section.
  • Store typed links between section nodes.
  • Confirm an exact-read section node exists.
  • Confirm relation paths against graph edges.
LadybugDB does not currently do
  • Load or crawl source documents.
  • Run the BM25-style or alias-vector ranking.
  • Call an embedding model or LLM.
  • Run as a separate pod or network service.

The in-memory reference store performs filtering and ranking. The Ladybug adapter verifies graph existence and traversal. Both sit behind the private KnowledgeStore interface, so a future Neo4j or search-service adapter can keep the public gateway capabilities unchanged.

Worked example · ORD-1003 investigation

How replacement evidence reaches the agent

  1. Question: Find authority, limits, approval, and precedence for a missing-order same-SKU replacement.
  2. Scope: commerce-demo, US, online, release commerce-us-2026-08-20, decision time 2026-08-20 18:00 UTC.
  3. Search: In-scope sections are ranked by the two deterministic lanes and connected one-hop relations are returned.
  4. Selection: The agent chooses demo-auto-recovery-bounds, demo-approval-thresholds, and demo-evidence-precedence.
  5. Exact reads: The gateway returns each section with its source and a separate signed receipt.
  6. Handoff: The agent sends those IDs and receipts to Commerce Core. The gateway itself never returns allowed.
What scales and what changes: The four public capabilities and domain-pack shape are reusable across domains. Each domain supplies its own sources, normalized sections, aliases, tags, relations, and golden cases. For a much larger corpus, the same API can sit in front of a production search and graph adapter; this demo's in-memory ranking and embedded projection are deliberately laptop-sized.

Commerce Core: six public capabilities

get_order_contextRead current order truth

Why it exists: The agent must not invent order facts.

Input: order_id.

What it does: Reads the order from Commerce Core. Returns payment, fulfillment, carrier, value, inventory, risk, restrictions, tenant, jurisdiction, channel, and version.

Changes data? No. Uses AI? No.

list_fulfillment_optionsList permitted action choices

Why it exists: The model may choose only from actions that the business service exposes.

Input: order_id.

What it does: Uses current order state to return possible option IDs such as wait, cancel and refund, merchandise refund, same-SKU replacement, or carrier claim. It also states each option's preconditions and evidence channel.

Changes data? No. Uses AI? No.

evaluate_recovery_policyMake the authoritative policy decision

Why it exists: An LLM must not decide whether a business action is authorized.

Input: Order ID, one option ID, release ID and hash, decision time, exact section IDs, and one signed receipt for every section.

  1. Reads the current order from Commerce Core.
  2. Checks that the supplied policy release is active.
  3. Verifies every evidence receipt, scope, date, and section.
  4. Applies fixed Go rules for the selected option.
  5. Applies refund or replacement approval thresholds.
  6. Returns one outcome and a short-lived decision token. Only an eligible decision can execute.

Possible outcomes: allowed, approval_required, denied, insufficient_evidence, or conflicting_evidence.

Changes data? It stores a short-lived decision, but does not change the order. Uses AI? No.

execute_recovery_commandApply one guarded business change

Why it exists: A decision must be checked again at the last possible moment.

Input: Decision token, duplicate-protection (idempotency) key, and—when required—checkpoint reference and runtime-generated approval proof.

  1. Returns the original result if the same idempotency key already completed.
  2. Checks that the decision was eligible.
  3. Checks the active policy release.
  4. Checks human approval for approval-class decisions.
  5. Checks the current order version and decision expiry.
  6. Revalidates evidence and recalculates the policy outcome.
  7. Applies the option-specific mutation and increases the order version.

Changes data? Yes. This is the only public mutation capability. Uses AI? No.

verify_order_outcomeCheck the business result

Why it exists: HTTP success does not prove that the expected order state exists.

Input: Order ID and command ID.

What it does: Reads the order and checks action-specific fulfillment, payment, carrier-claim, command, and recovery postconditions.

Output: verified=true only when the expected state is present.

Changes data? No. Uses AI? No.

send_synthetic_notificationRecord communication after verification

Why it exists: Customer communication must not claim success before the business result is verified.

Input: Order ID, command ID, channel, and a customer-safe message.

What it does: Confirms the command postconditions and stores a local notification record. It does not send a real email or message.

Changes data? Adds a synthetic audit record. Uses AI? No.

Knowledge Gateway: four public capabilities

get_release_infoIdentify the active policy release

Why it exists: Every decision must identify the exact policy snapshot it used.

Input: Optional release ID; otherwise use the active release.

Output: Release ID, content hash, domain, tenant, validity dates, source count, and section count.

Changes data? No. Uses AI? No.

search_evidenceFind relevant policy sections

Why it exists: The corpus can be much larger than an agent prompt or skill.

Input: Natural-language query, tenant, jurisdiction, channel, decision time, optional release and tags, and a result limit.

  1. Filters by tenant, release, jurisdiction, channel, and effective date.
  2. Ranks the remaining sections using BM25-style word relevance.
  3. Also ranks them using alias-aware hashed vectors and cosine similarity.
  4. Combines the two lists using reciprocal-rank fusion.

Output: Ranked candidate objects with normalized section content, IDs, source metadata, scores, retrieval methods, matched terms, optional relation paths, and warnings.

Important: Search candidates are not yet authorization evidence. The agent must read decisive sections exactly.

Changes data? No. Uses AI? No.

traverse_relationsFollow explicit policy links

Why it exists: A useful answer may depend on an exception, prerequisite, authority, conflict, or procedure connected to the first section.

Input: Starting section IDs, scope, decision time, optional relation types, maximum depth, and result limit.

What it does: Follows typed graph relationships. The agent's plan guard fixes the demo to one hop and at most twenty paths.

Output: Paths containing source section, relation type, target section, and depth.

Changes data? No. Uses AI? No.

read_exact_sectionRead and prove one decisive section

Why it exists: A ranked search candidate—even one containing section text—is not a safe decision basis without scoped proof.

Input: Exact section ID, tenant, jurisdiction, channel, decision time, and optional release ID.

What it does: Checks scope and effective dates, returns the normalized section and source, and signs a receipt bound to that exact read.

Receipt lifetime: Thirty minutes in this demo.

Changes data? No business change. Uses AI? No.

How a large corpus is reduced safely

This is more than a simple word search

The gateway removes out-of-scope sections first. It then combines exact word matches with curated meaning aliases, follows declared policy relationships, and returns a small candidate list. The agent must still read every decisive section exactly. Finally, Commerce Core—not search—decides whether action is authorized.

  1. Large corpusMany documents and sections
  2. Scope filterRight tenant, place, channel, date, and release
  3. Hybrid rankWord matches plus curated meaning aliases
  4. Exact evidenceFull sections, sources, hashes, and signed receipts
  5. Policy codeOne governed decision

What this demo contains

The commerce pack is about 26 KB: seven sources and eighteen normalized sections. Its source records include FTC, eCFR, USPS, FedEx, Target, and Walmart public material, plus one synthetic internal recovery standard. The included text is a curated demo snapshot; it is not a live legal feed.

What “2–10 MB” means

It was an early local-demo sizing guide, not a real-world upper limit. A production corpus can be far larger. The gateway API can stay the same while its storage adapter moves from embedded LadybugDB to a larger graph or search service.

What “semantic” means here

This local version does not call an embedding model. Domain-pack authors provide deterministic aliases that connect related wording. This makes tests repeatable, but it is not a general vector search system.

Hidden controls used only by the demo

The setup script and paired tests need controlled ways to reset state, prove the normal no-AI path, simulate a state change, and switch domain packs. These capabilities are marked internal, so the agent cannot discover or choose them.

  • process_normal_order — checks a healthy order without an agent or LLM.
  • manage_demo_state — resets or deliberately changes synthetic Commerce state.
  • manage_demo_domain_pack — activates an allow-listed bundled domain pack.

The approval proof is not an LLM instruction

The agent runtime creates a proof from the approved checkpoint, decision token, and duplicate-protection identity. Commerce Core verifies it. The raw proof is sent only to the guarded command call. New Registry, checkpoint, LLM debug, trace, and log records redact or omit it.

Chapter 11

Multiple requests, workers, and scale

A pod is a service instance. A worker is a goroutine inside the agent pod. They are not the same thing.

2active top-level tasks
98tasks waiting in Redis

1 pod × 2 workers = 2 task slots

Important demo limit

The calculator explains the worker model. It does not mean that the complete demo is ready for ten agent pods. Commerce Core currently keeps order state in the memory of one pod. Safe horizontal scaling needs a shared transactional database with order-version and duplicate-protection constraints.

Travel Chat Agent

Each normal chat runs directly in a lightweight Go request handler. Its live response connection stays open. There is no application task queue for normal chat.

Order Operations Agent

The webhook returns HTTP 202. Redis holds the task. A fixed worker pool controls how many slow investigations run at once.

Known Registry Viewer limitations

The business behaviours passed, but some presentation fields are still inaccurate or incomplete. In particular, do not rely on the displayed combined duration, zero DAG step durations, implied cross-phase parallelism, or automatic joining of a human-approval interruption with its resume execution.

The LLM Calls view contains the raw synthesis draft. The structured task result and governed application response are authoritative.

Chapter 15

Glossary

Use this section when you meet an unfamiliar term.

AI
Artificial intelligence. In this demo, the AI component is a large language model used by the agent.
AI agent
Software that gives a language model an objective, instructions, and controlled tools.
API
Application Programming Interface. A defined way for software services to call each other.
Capability
One named operation exposed by a tool service, such as reading an order or evaluating policy.
Checkpoint
Saved execution state created before a sensitive step so a person can approve, reject, or abort it.
Deterministic
Produces the same result from the same validated input without model judgement.
Domain pack
A versioned collection of normalized policy sections, sources, dates, graph relations, search aliases, and tests.
Corpus
The full collection of documents or policy sections that the gateway can search.
Event
A small message saying that something happened and may need work, such as an order becoming missing in transit.
Evidence receipt
A short-lived signed statement proving that one exact policy section was read in a particular release and scope.
Graph database
A database that stores records and named relationships between them. The demo uses it for links such as “requires” and “overrides”.
Goroutine
A lightweight unit of concurrent work managed by the Go programming language runtime.
HITL
Human in the loop. The workflow pauses before a sensitive action and waits for a person.
Idempotency
A safety property that makes a repeated request return the original result instead of applying the business action again.
Jaeger
A trace viewer that shows calls across services.
JSON
A structured text format used for requests and responses between services.
Kind
A tool that runs a local Kubernetes cluster using containers.
Kubernetes
A platform that runs and manages containerised services.
LadybugDB
The embedded graph database library used for the gateway's disposable section-and-relation projection. It is not a separate service and does not currently perform relevance ranking.
LLM
Large language model. It helps the agent plan and summarise.
Mutation
A business data change. Creating a replacement and increasing the order version is the main mutation in this demo.
Pod
One running Kubernetes instance of a service.
Policy release
An immutable, identified snapshot of policy knowledge and deterministic thresholds.
Redis
A shared data service used here for discovery, tasks, deduplication, skills, and checkpoints.
Registry
The stored execution record containing plans, steps, skills, LLM interactions, and HITL snapshots.
Scope
The limits that decide where evidence applies, such as tenant, country, sales channel, and date.
Skill
A small operating procedure injected into agent planning. It is not the large domain corpus.
Tool service
A normal web service that exposes controlled capabilities to an agent.
Trace
A connected record of calls made across services during one execution.
Webhook
An HTTP address that accepts an event from another system.
Worker
A long-running goroutine inside the agent process that takes queued tasks from Redis.
